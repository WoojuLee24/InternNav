# S2 look_down 프레임 해상도 이슈 — 원인·수정·검증

lite 배포판(`InternVLA-N1-lite2-DualVLN`, GGUF S2 + TRT S1)이 원본(`InternVLA-N1-DualVLN`, 7B in-process)보다 Isaac Sim eval에서 느리고 부정확했던 원인과 수정, 그 인과를 뒷받침하는 실측 결과.

## 문제 1: 입력 해상도
### 원인 

lite eval 로그에서 S2가 "카메라를 아래로(look_down)" 낸 뒤 다시 물어봐도 계속 look_down만
반복하는 루프가 발견됐다. **재시도 로직 자체는 정상**(orig·lite가 `internnav/agent/internvla_n1_agent.py`를
공유, orig에서는 이 루프가 0건). 문제는 look_down 프레임의 **입력 해상도**였다:

- orig: planning 384×384, **look_down은 원본 카메라 해상도(640×480)** (`internvla_n1_policy.py:127-128`)
- lite(수정 전): 전부 **448×448 고정**

낮은 해상도로는 waypoint 좌표를 못 찍고 "다시 봐야겠다"는 답만 반복한 것.

### 수정 (3파일, 옵션 기본값에서 기존 동작 100% 보존)

| 파일 | 변경 |
|---|---|
| `internvla_n1_policy_llamacpp.py` | `lookdown_full_res`(기본 `False`) 추가 + `s2_step()` guard clause — `True`일 때만 look_down에 원본 해상도 사용 |
| `internvla_n1_agent_llamacpp.py` | config → policy 전달 1줄 |
| `h1_internvla_n1_async_lite_cfg.py` | `resize_w/h: 448→384`, `lookdown_full_res: True` 추가 |


| 지표 | 고정(수정 전, 08-12T11:38) orig/lite | 고정 안 함(수정 후, 08-13T05:30) orig/lite |
|---|---|---|

수정 후 완전히 사라지고 orig과 동등~우위로 바뀐 것.

## 문제 2: S2 per-call latency — lite가 planning 호출에서 더 느림

`sim loop steps/s`는 렌더링·폴링이 섞인 종합치라 모델 속도와 분리가 안 된다. eval에서 켜지는
`VLN_TIMING` p50(08-13T05:30)은 S1 142.6 → 13.0 ms(**11x**, TRT), S2 315.9 → 575.0 ms(**0.55x**).
S1 이득은 명확한데 S2가 왜 느린지는 이 값만으로 알 수 없어, Isaac 없이 `s2_step()`만 재는 벤치를
새로 만들었다 (`verify/verify_s2_latency.py`, 이미지 장수 스윕).

```bash
/workspace/isaaclab/_isaac_sim/python.sh vln-deploy/verify/verify_s2_latency.py --n 11 --variant lite --history 0,2,4,8 --warmup 1
```
`--variant orig`으로 한 번 더 돌린다(7B 16 GB + 러너 7 GB 동시 상주는 OOM. CSV는 누적 병합).
orig이 `flash_attention_2`를 쓰므로 **Isaac 인터프리터 필수** — `convenv_x86`에는 flash_attn이 없다.

### 결과 — 격차는 전부 "이미지 장당 비용"

| 이미지 장수 | orig | lite (PNG, 수정 전) | lite (BMP, 수정 후) |
|---|---|---|---|
| 1 | 78.5 ms | 84.1 ms | 63.2 ms |
| 3 | 119.1 | 201.7 | 136.3 |
| 5 | 170.3 | 310.1 | 201.6 |
| 9 (eval 실전 조건) | **293.0** | **539.1** (1.84x) | **337.7** (1.15x) |
| 장당 기울기 | 26.4 ms | 56.7 ms | 34.3 ms |

1장이면 원래도 동급(1.07x)이었다. 9장 행의 1.84x가 eval p50 비율(575.0/315.9 = 1.82x)과 일치하므로
이 벤치가 eval 관측을 그대로 재현한다.

### 단계별 분해 (9장, 수정 전)

| 단계 | orig | lite |
|---|---|---|
| 이미지 준비 | 34.5 ms (HF processor) | **200 ms** (PNG 저장 22.2 ms × 9장) |
| 비전 인코딩 | 73.7 ms (배치 ViT 1회) | 134 ms (15 ms × 9회 순차) |
| 파일 디코드(러너측) | — | ~22 ms |
| LLM prefill + 생성 | ~185 ms (1764 tok) | ~183 ms (1296 tok) |
| **합계(실측)** | **293.0 ms** | **539.1 ms** |

- **주범은 PNG 저장.** `_save()`가 매 s2_step마다 모든 이미지를 PIL 기본 압축으로 디스크에 쓴다.
  22 ms의 정체는 I/O가 아니라 zlib 압축이다 — 같은 크기 BMP는 0.29 ms
  (PNG 기본 21.4 / `compress_level=0` 3.4 / BMP 0.29 / JPEG q95 0.41). llama.cpp가 아니라 우리 코드 비용.
- 순차 인코딩은 2번째 요인 (장당 14.9 vs 6.85 ms, `clip.cpp:829`의 batch=1 제약).
- **Q4_K_M은 지연시간에 거의 중립.** prefill은 orig이 1.44x 빠르고(216.7 vs 311.8 ms), decode는 lite가
  3.5x 빠르다(14.03 vs 3.96 ms/tok). 출력이 `↓`나 좌표 몇 토큰뿐이라 손익분기(≈9토큰) 근처에서 상쇄된다.
  양자화의 속도 이득은 긴 생성에서만 나온다(128토큰이면 orig 1998 vs lite 704 ms).

### 수정 (적용)

| 파일 | 변경 |
|---|---|
| `internvla_n1_policy_llamacpp.py` | `_save()` PNG → **BMP** (무손실) |

BMP 무손실성은 실측으로 확인했다: 같은 이미지를 PNG/BMP로 저장해 러너에 넣으면 생성 텍스트 6/6 동일,
**LATENT float32 벡터도 6/6 비트 동일** → 러너가 디코드한 픽셀이 완전히 같다(정확도 영향 0).
파일을 아예 없애는 것도 가능하지만(`mtmd_bitmap_init`이 raw RGB를 받음) BMP 대비 0.29 → ~0.05 ms라 실익 없음.

**eval 검증 (`compare_eval.sh -n 10`, 2026-08-20)**

| 지표 | orig | lite 수정 전 | **lite BMP** |
|---|---|---|---|
| S2 p50 | 322.5 ms | 575.0 ms (0.55x) | **319.1 ms (1.01x, 동급)** |
| S1 p50 | 137.8 ms | 13.0 ms | 12.7 ms (10.9x) |
| sim loop | 5.93 steps/s | 6.52 | **7.70 (orig의 1.30x)** |
| SR / SPL | 0.70 / 0.666 | 0.70 / 0.630 | 0.60 / 0.513 |

SR 0.10 차이는 n=10 노이즈다 — 같은 config의 **orig도 08-13 실행에서 0.60, 08-20 실행에서 0.70**으로
1 에피소드만큼 흔들렸다(Isaac 물리·렌더 비결정성, `260804_gs_vlnpe_reproducibility_limits.md`).
정확도 판정은 에피소드 수를 늘려야 한다.

### 기각: `kv_reuse=True` (SR 0.70 → 0.40)

배포 스택(`run.sh async`)의 기본값이라 eval에도 적용해 봤다. 호출당 이미지가 9장 → 1장이 되어
**S2 p50 76.6 ms (orig 대비 4.21x)** 까지 떨어졌지만 정확도가 무너졌다:

| | orig | lite (kv_reuse=True) |
|---|---|---|
| SR / SPL | 0.70 / 0.666 | **0.40 / 0.291** |
| NE / TL | 2.18 / 10.9 | 6.08 / 16.5 |
| 스텝 수 (10 ep) | 1,817 | **4,964** (2 에피소드가 상한 1100까지 헤맴) |
| sim loop | 5.93 steps/s | 5.67 (모델은 4.2x 빠른데 **더 느림**) |

원인은 프롬프트 구조 변경이다: 히스토리가 프롬프트 내 이미지 목록이 아니라 멀티턴 KV로 들어가고
instruction이 매 턴 반복되어 학습 시 형식과 달라진다. 호출당 이득을 스텝 수 증가가 전부 먹었다.
→ `kv_reuse=False` 유지. (배포 스택의 `--kv-reuse` 기본 True도 정확도 근거가 없어 보이므로 재검토 필요.)

**미결**: eval의 `resize 384`는 clip.cpp가 112 배수로 내림해 실제 **336 px / 144토큰**이 된다
(orig은 28 배수 올림으로 392 px / 196토큰). 112 정렬 제약상 196토큰 정확 재현은 불가능.
336 vs 448 A/B 실측(`verify_lookdown_resolution.py --n 30 --resize {336,448}`)은 **차이 없음**:
planning 336 + look_down 원본 = 30/30, planning 448 + look_down 원본 = 29/30. → 현 설정 유지.
같은 실험에서 look_down을 고정 해상도로 낮추면 336 → 12/30(40%), 448 → 20/30(67%)로 무너져
`lookdown_full_res=True`의 근거가 다시 확인됐다.

### KV 캐시 조건 — planning은 같았고 look_down은 달랐다

`kv_reuse=False`(수정 전) 기준:

| 호출 | orig | lite | 조건 |
|---|---|---|---|
| planning | `generate(past_key_values=None)` → 매번 full prefill | 매 스텝 `RESET` (s2-runner.cpp:68) | **동일** |
| look_down | 대화 전체 재처리 → ViT+prefill 전부 재계산 | RESET 없이 새 프레임 1장만 추가, KV 재사용 | **다름** |

실측(n=6 median): planning orig 344.5 / lite 535.0 ms, look_down orig **525.8** / lite **155.5** ms.
orig은 look_down이 planning보다 비싸고 lite는 3.4x 싸다. 위 장수 스윕은 planning만 쟀으므로 공정하지만,
**eval `s2` p50에는 두 종류가 섞여 있다** — 문제 2는 planning 기준으로 봐야 한다.

## 명령어 옵션 요약

**`verify/compare_eval.sh`**

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `-n N` | 5 | 비교 에피소드 수 |
| `-t N` | 128 | S2 생성 토큰 길이 (양쪽 동일 적용, 공정 비교 핵심) |
| `--native-tokens` | - | 토큰 길이 안 맞춤 (디버깅용, 불공정) |
| `-v lite\|orig\|both` | both | 실행 대상 |
| `--lite-model PATH` | **존재하지 않는 경로** — 반드시 명시 | lite 체크포인트 |
| `--orig-model` / `--lite-config` / `--orig-config` | 기본 경로 | 경로 override |
| `--keep-lmdb` / `--no-timing` / `--dry-run` | - | lmdb 안 지움 / 세부 계측 생략 / 커맨드만 출력 |

> `--lite-model /ws/src/InternNav/checkpoints/InternVLA-N1-lite2-DualVLN` 항상 명시할 것.

**`verify/verify_lookdown_resolution.py`**: `--n`(기본 30, 샘플 수), `--resize`(기본 384, 고정 조건 크기), `--samples-dir`(기본 `quantization_kit/data/vln-ce/samples`)

**`verify/verify_s2_latency.py`**: `--n`(샘플 수), `--variant lite|orig|both`, `--history`(장수 스윕, 기본 `0,2,4,8`), `--warmup`(조건별 제외 개수), `--lite-model`, `--out`(기본 `verify/compare_out/s2_latency.csv`)

**관련 config 키** (`h1_internvla_n1_async_lite_cfg.py`)

| 키 | 의미 |
|---|---|
| `resize_w`/`resize_h` | planning/히스토리 이미지 리사이즈 크기 |
| `lookdown_full_res` | `True`=look_down만 원본 해상도 (orig과 동일) |
| `kv_reuse` | S2 러너 멀티턴 KV 캐시 재사용 여부 |
| `use_trt_s1` | S1을 TensorRT FP16으로 돌릴지 |
| `s1_steps` | S1 denoise 스텝 수 |
| `num_history` | planning에 넣는 과거 프레임 수 상한 |

## 결론

- **문제 1**: 결과 A(eval 지표)와 결과 B(pixel_goal 성공률)는 같은 원인(look_down 해상도 불일치)의
  서로 다른 관측이다. 해상도를 orig과 맞추자 양쪽 다 즉시 회복됐다.
- **문제 2**: lite S2가 느린 건 양자화 탓이 아니라 **이미지를 매 호출 PNG로 압축해 파일로 넘긴 비용**이
  가장 크고(장당 22 ms), 순차 인코딩이 그 다음이다. BMP + `kv_reuse=True`로 planning 호출은
  539 → 337 ms(9장 기준)까지 내려간다. Q4 자체는 지연시간에 중립(decode는 3.5x 빠르지만 출력이 짧아
  이득이 안 쌓임).

초기 계측 이력은 `.claude/memory/eval_timing_incremental_flush_result.md` 참고.
