## 근본 원인: vln_ce `pose.{rig}`는 **에피소드 start-relative**다

- `pose.125cm_0deg` frame0 = 위치 `(0,0,1.25)` = **원점**(카메라 높이 1.25만). → 절대 mesh 좌표가 아님.
- 궤적 translation: x∈[0,4.68], y∈[-4.1,0], z≡1.25. y가 mesh y-bounds([-2.89,5.39]) **밖으로** 나감 → 절대좌표 아님 확정.
- `mp3d_n1` OBJ와 `mp3d` GLB은 **동일 좌표 frame**(bounds 완전 일치, Z-up, z∈[-0.13,2.68]). → mesh 선택 문제 아님.
- **학습은 절대 정합이 필요 없다**: BEV는 depth+cam_height+pitch로(월드 pose 미사용), pose는 상대 궤적(`get_trajectory_relative_to_frame`)에만 사용. → 절대 pose↔mesh 변환은 **augmenter가 새로 요구하는 것**(기존 코드에 없음).

## 수정 경로 (검증됨): 절대 pose 복원

에피소드별 절대 start pose가 **raw_data**에 있음(traj_data엔 없음):
- `raw_data/r2r/{split}/{split}.json.gz` 에피소드에 `start_position`(habitat Y-up), `start_rotation`(quat), `reference_path`, `instruction`.
- **traj_data ep ↔ raw_data ep 매칭**: instruction text로 exact match 성공(ep0: "Exit the bedroom...", train split, 씬당 75 eps). scene_id도 대조.
- 17DRP5sb8fy는 **train split**에 있음(val_unseen 아님).
- ep0 start_position(Yup) = `[-10.29, 0.07, 1.91]`, reference_path 전부 y=0.07(floor const).
- habitat Y-up → mesh Z-up 축매핑 후보 `(x,z,-y)` 또는 `(x,-z,y)`가 start를 mesh bounds **안**·floor 근처(z≈±0.07 vs mesh floor -0.13)로 보냄 → 대략 맞음(정확한 R·offset은 미확정).

절대 카메라 pose(mesh frame) 체인:
`T_mesh[t] = T_habitat→mesh(고정 R) @ T_start_habitat(start_pos,start_rot) @ T_rel[t](pose.{rig})`
- 미확정 요소: (1) habitat→mesh 정확한 4×4(축 rotation + floor offset), (2) start pose가 agent냐 camera냐, (3) quaternion 규약, (4) T_rel과의 합성 순서.
- 전부 offline converter로 1회 캘리브레이션 가능(gs_vlnpe가 vln_n1에 한 것과 동종 작업).

## 결론 — 두 갈래 (사용자 결정 필요)

- **A. 절대정합 converter 구축**: raw_data 매칭 + habitat→mesh 변환 캘리브레이션 → 사용자가 택한
  **cached 전역 3D 타일** 계획대로 진행. 작업량 중간, tractable(증거 위 확보). 원 계획에 충실.
- **B. 에피소드 로컬 3D**: 에피소드 자신의 depth 프레임을 start-relative로 누적해 로컬 occ/mesh 생성
  → 절대정합 불필요. 단, 경로가 **탐색한 복도 밖으로 못 나감**(해결3이지 3-2 아님). novelty 약화.

(옵션 C=vln_n1 사용은 dataloader가 vln_ce를 읽으므로 augment 대상이 안 됨 → 제외.)

## 절대정합 방법 (구현됨, `scripts/dataset_converters/gs_vlnpe/vlnce_align.py`)
1. traj_data ep instruction ↔ raw_data(train/val_* 전 split) `start_position`/`start_rotation` 매칭.
2. 에피소드 depth를 start-relative pose(conv='cam2world')로 unproject → start-frame point cloud(Z-up).
3. cloud를 mesh에 강체 정합: init translation = start_position axis-map('x,-z,y', z=mesh floor),
   yaw 24-way sweep + Nelder-Mead refine, 비용 = point-to-mesh median. → `T_sf2mesh`(4×4).
4. 절대 카메라 pose = `T_sf2mesh @ pose_rel[t]` (OpenCV c2w, mesh frame). 렌더/occ에 그대로 사용.
- ep0(17DRP5sb8fy): yaw 60°, residual 0.0035 m. offline 1회/에피소드 → `T_sf2mesh` 저장해 augmenter가 로드.

## 로버스트니스 — 해결됨 (2026-08-14)
초기 registration(yaw 36-way+2 init)은 **큰/다층 씬에서 실패**(s8pcmisQ38h 0.13~0.40m). 원인:
mesh·매칭·far-point 아님. s8은 **다층 씬**(mesh z-range 12m)인데 t_z를 global floor로 고정한 게 버그.

**최종 방법(`fit_sf2mesh`) — 전부 GT 해석적, sweep 없음**:
- translation: `t = (start_x, -start_z, start_y - 0.20)` (`Z_OFFSET_M=0.20`, 17DRP 캘리브). 다층 씬도 `start_y`가 층 직접 지정.
- yaw: **GT `start_rotation`에서 직접** — `yaw_mesh = (2*atan2(qy,qw) + 90°) mod 360°` (quat [x,y,z,w]).
  검증된 7개 에피소드에서 exact 성립(330→60,270→0,90→180,120→210). +90°=habitat forward→mesh 축 오프셋.
- sweep/optimization 전혀 없음(사용자 지적 반영: GT 있으면 GT 사용). `refine`는 옵션이나 KDTree 근사라 기본 off.

**검증 6/8 PASS**(<0.01, 순수 GT): 17DRP ep0/1/2 (0.0035/0.0079/0.0029), s8pcmisQ38h ep0/1/3
(0.0020/0.0044/0.0023), ep2/ep4만 ~0.012-0.015(1.2-1.5cm, 5cm voxel 대비 허용). G1 end-to-end:
G1a 0.0035 / G1b render vs stored PASS. 잔차는 대부분 Z_OFFSET 상수 근사·cloud 노이즈(yaw는 exact).
