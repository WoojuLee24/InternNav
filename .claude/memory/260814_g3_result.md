## 판정: FEASIBLE (v1 depth-only)

17DRP5sb8fy, 렌더 224×224, 타일 tile_0_0(154k faces).

| 연산 | 시간 | 빈도 |
|---|---|---|
| planning (occ→2D→A*+refine+spline) | **3.4 ms** | sample당 |
| depth 렌더 per-frame (RGB 생략) | **9.9 ms** | 프레임당(타일 상주) |
| 타일 add_geometry | 66 ms | 타일 전환 시에만(LRU) |
| renderer init | 72 ms | worker당 1회 |
| 타일 파일 load | 105 ms | 타일당 1회(캐시) |

per-sample (타일 캐시): T=1 13 / T=5 **53** / T=10 102 ms. 타일 전환 sample: T=5 118 ms.
→ T=5 캐시 53ms는 현 dataloader의 다중 jpg/png IO(수십~수백 ms)보다 작거나 비슷 → **감당 가능**.

## 핵심 최적화 (P-B augmenter가 반드시 반영)
1. **depth-only 렌더**: `render_to_image`(RGB) 생략 → 9.9 ms/frame (rgb+depth는 42 ms). v1은 depth만 쓰니 무손실.
2. **타일 씬 상주**: `render_along`은 매 호출 clear+add(66ms)+rgb+depth라 부적합. augmenter는 타일을 씬에
   **한 번 add**하고(타일 전환 시에만 갱신) 프레임마다 `set_camera_pose + render_to_depth_image`만.
3. planning은 `03_sample_gt_paths.plan_episode` 그대로 재사용(3.4ms).
4. (옵션) 타일 전환 잦으면 offline 타일 decimation(face↓)으로 add·frame 추가 절감. `fast_simplification` 미설치.
